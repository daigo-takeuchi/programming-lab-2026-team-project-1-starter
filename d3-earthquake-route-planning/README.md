## 1. 研究テーマと目的

**D3：東京圏での大地震発生時の交通規制・道路閉鎖を考慮した経路探索**

東京圏で大地震が起きた場合を想定し、**道路閉鎖や交通規制の下で、一般車両と緊急車両が通行できる経路**を探索します。
中心課題は、**BFS（幅優先探索）・Dijkstra 法・A* 探索を比較し、道路閉鎖・車両別の交通規制が、経路の到達可能性・移動距離・探索効率に与える影響を分析する**ことです。

| | 問い |
| --- | --- |
| RQ1 | **地震による道路閉鎖は経路にどう影響するか**：到達できるか、最短経路がどう変わるか、移動距離がどれだけ増えるか、代替経路があるか |
| RQ2 | **一般車両と緊急車両では最適経路がどう変わるか**：通常通行・完全閉鎖・緊急車両のみ通行可・コスト増加の各状態の影響 |
| RQ3 | **探索アルゴリズムによって結果はどう変わるか**：経路の有無、ホップ数、総移動距離、総移動コスト、展開ノード数、実行時間 |
| RQ4 | **道路閉鎖の規模と探索効率の関係**：ノード数 V、道路数 E、閉鎖率、緊急車両専用道路の割合、コストの分布、出発地・目的地 |

学習段階に応じて、課題を2層に分けています。

- **Core Research（必須課題）**：架空の道路ネットワークと固定の地震シナリオで、BFS・Dijkstra 法・A* を比較する
- **Advanced Research（発展課題）**：ランダムな閉鎖と到達可能性、緊急車両優先、時間変化、実際の道路データ、多目的最適化

このリポジトリには、BFS・Dijkstra 法・A*（h = 0）と小さなサンプルだけを用意しています。**直線距離のヒューリスティックや大規模な実験は学生の課題**です。完成済みの災害対応・交通管制システムではありません。

## 2. 東京圏の大地震と道路ネットワーク

大地震が起きると、建物の倒壊・橋の損傷・液状化・火災などで、道路が通れなくなることがあります。また、救急・消防などの**緊急車両の通行を確保するため、一般車両の通行が規制される道路**が設定されることがあります。

このような状況では、「普段の最短経路」が使えず、

- そもそも目的地に**到達できるか**
- 通れる道路だけで**どの経路が最短か**
- 一般車両と緊急車両で**経路がどう違うか**

を、道路ネットワーク上の探索で調べる必要があります。

### サンプル道路ネットワーク（`data/sample_tokyo_network.json`）

東京圏をイメージした**架空の**道路ネットワークです（ノード 10、道路 15）。

## 3. グラフ理論の基礎

道路ネットワークを**グラフ G = (V, E)** として表します。

| 用語 | 道路ネットワークでの意味 |
| --- | --- |
| ノード（頂点）V | 交差点・地区 |
| エッジ（辺）E | 道路 |
| 重み | 道路の距離、または移動コスト |
| 経路 | 道路をたどってノードからノードへ行く道 |
| ホップ数 | 経路で通る道路の本数 |

Core Research では**無向グラフ**（どの道路も双方向に通行できる）を使います。一方通行は Advanced Research で扱います。

### データの表し方（`road_network.py`）

```python
network = {
    "nodes": {"SJK": {"name": "Shinjuku", "x": 0, "y": 5}, ...},
    "roads": [{"from": "SJK", "to": "IKB", "distance": 4.4, "status": "open", "cost_multiplier": 1.0}, ...],
}
```

| 関数 | 内容 |
| --- | --- |
| `load_network(path)` | JSON の読み込みと検証（重複キーも検出） |
| `validate_network(network)` | 端点が存在する、自己ループがない、重複道路がない、距離・倍率が正の有限数、通行状態が定義済み |
| `node_ids`、`roads`、`node_name`、`find_road` | ノード・道路の取得 |
| `can_pass(road, vehicle)` | その車両が道路を通行できるか |
| `road_distance(road)`、`road_cost(road)` | 距離、移動コスト（距離 × コスト倍率） |
| `adjacency(network, vehicle)`、`neighbors(...)` | その車両が**通行できる道路だけ**を使った隣接リスト（無向なので両方向に登録） |
| `euclidean_lower_bound_violations(network)` | 「距離 < 直線距離」の道路の一覧（A* の許容性の確認用） |

孤立ノード（道路がつながっていないノード）や、道路が1本もないネットワークも扱えます。

## 4. 道路閉鎖と交通規制

### 道路の通行状態

| status | 一般車両 | 緊急車両 | 意味（教育用の架空の規則） |
| --- | :---: | :---: | --- |
| `open` | ○ | ○ | 通常通行可能 |
| `closed` | × | × | 完全閉鎖（物理的に通行できない） |
| `emergency_only` | × | ○ | 緊急車両のみ通行可能 |

さらに、`cost_multiplier`（コスト倍率）で、通行はできるが時間がかかる道路を表します。**移動コスト = 距離 × コスト倍率**です。

> これらは教育用に定義した**架空の規則**であり、実際の法令や災害時の交通規制を再現したものではありません。

### 地震シナリオ（`disaster.py`）

Core Research では、シナリオを**固定データ**として定義しています（毎回同じ結果になります）。

| シナリオ | 内容 |
| --- | --- |
| `before`（Scenario 0） | 地震発生前：すべての道路が通常通行可能 |
| `closure`（Scenario 1） | 上野–江東、東京–江東 を**完全閉鎖** |
| `regulation`（Scenario 2） | 池袋–上野 を**緊急車両のみ**通行可能に |
| `congestion`（Scenario 3） | 上野–江東 のコスト × 2.0、新宿–東京 のコスト × 1.5 |

`apply_scenario(network, name)` や `apply_changes(network, closed=..., emergency_only=..., cost_multipliers=...)` は、**元のネットワークを変更せず、独立したコピー**を返します。同じ道路を閉鎖と規制の両方に指定した場合は、閉鎖が優先されます。ランダムな閉鎖シナリオは Advanced A の課題です。

## 5. 一般車両と緊急車両

経路探索の関数には、車両の種類 `"general"`（一般車両）または `"emergency"`（緊急車両）を渡します。どのアルゴリズムも、**その車両が通行できる道路だけ**を使います。

- 一般車両は、`emergency_only` の道路を通行できません。
- **緊急車両であっても、`closed`（物理的に通行できない）道路は通行できません。** 「緊急車両はどこでも通れる」という前提は誤りです。

### `starter.py` の結果（新宿 → 江東、Dijkstra 法）

| シナリオ | 車両 | 経路 | 距離 | 移動コスト | 地震前との差 |
| --- | --- | --- | ---: | ---: | ---: |
| 地震発生前 | 一般 | 新宿 → 池袋 → 上野 → 江東 | 15.4 | 15.4 | — |
| 道路閉鎖 | 一般・緊急 | 新宿 → 渋谷 → 品川 → 豊洲 → 江東 | 18.2 | 18.2 | +2.8 |
| 交通規制 | **一般** | 新宿 → 東京 → 江東 | 16.8 | 16.8 | +1.4 |
| 交通規制 | **緊急** | 新宿 → 池袋 → 上野 → 江東 | 15.4 | 15.4 | ±0 |
| 混雑 | 一般・緊急 | 新宿 → 渋谷 → 東京 → 江東 | 17.6 | 17.6 | +2.2 |

- **道路閉鎖**では、閉鎖は両方の車両に効くので、一般車両と緊急車両の経路は同じになります。
- **交通規制**では、緊急車両だけが池袋–上野を通れるので、**一般車両と緊急車両で経路が変わります**。
- **混雑**では、距離が最短の経路（新宿 → 池袋 → 上野 → 江東、距離 15.4）は移動コストが 21.4 に増えるため、**距離は長くてもコストの小さい経路**が選ばれます。距離とコストの違いに注目してください。

## 6. BFS（`routing.bfs`）

**通る道路の本数（ホップ数）が最小**の経路を求めます。

1. 出発ノードを**キュー**に入れる。
2. キューからノードを取り出す（目的地なら終了）。
3. 通行できる道路でつながった、まだ見つけていないノードをキューに入れ、どこから来たか（親）を記録する。
4. キューが空になるまで繰り返す。空になったら**到達できない**。
5. 目的地から親をたどって**経路を復元**する。

キューには教科書 第4章の **`FixedQueue`** を使っています（11章）。

> ⚠️ **BFS は道路の距離やコストを見ないので、総距離・総移動コストが最小になるとは限りません。**
> 地震前の新宿 → 江東では、BFS は 新宿 → 東京 → 江東（**2本**、コスト 16.8）を返しますが、コスト最小の経路は 新宿 → 池袋 → 上野 → 江東（3本、コスト **15.4**）です。BFS の「最小ホップ数」と、Dijkstra 法の「最小移動コスト」を混同しないでください。

## 7. Dijkstra 法（`routing.dijkstra`）

**総移動コストが最小**の経路を求めます。移動コストが**非負**であることが前提です。

1. 出発ノードのコストを 0 とし、**優先度付きキュー**（Python 標準の `heapq`、二分ヒープ）に入れる。
2. キューから**コストが最小**のノードを取り出す（目的地なら終了）。
3. そのノードのコストを確定し、隣のノードについて「ここを通った場合のコスト」が今までの記録より小さければ、記録を更新してキューに入れる。
4. キューが空になるまで繰り返す。

同じノードの候補がキューに複数残ることがあるので、取り出したときに**確定済みのノードや、記録より大きいコストの古い候補は読み飛ばします**。

## 8. A* 探索（`routing.a_star`）

**f(n) = g(n) + h(n)** が小さいノードから展開します。

- **g(n)**：出発地から n までの累積移動コスト
- **h(n)**：n から目的地までの**推定**残余コスト（ヒューリスティック関数）

```python
routing.a_star(network, start, goal, vehicle)                                    # h(n) = 0
routing.a_star(network, start, goal, vehicle, heuristic=routing.euclidean_heuristic)  # 学生が実装
```

- `starter.py` では **h(n) = 0**（`zero_heuristic`）を使っています。このとき A* は **Dijkstra 法と同じ探索**になります（展開ノード数も同じ）。
- 学生は `euclidean_heuristic`（直線距離）を実装し、A* の展開ノード数が減るかを調べてください（9章）。

### A* の正しさの検証

同じ車両・同じ道路ネットワーク・同じ移動コストなら、**適切なヒューリスティック**と正しい実装のもとで、**A* と Dijkstra 法の最小移動コストは一致**します。`tests/test_routing.py` は、すべての出発地・目的地の組でこれを確認します（`euclidean_heuristic` のテストは、未実装の間スキップされます）。最小コストの経路が複数ある場合、**経路そのものは違ってもかまいません**。

### 展開ノード数の定義（3方式で共通）

**キューから取り出したノードのうち（優先度付きキューでは古い候補を除き）、実際に隣接する道路を調べたノードの数**です。目的地を取り出した時点で探索を終えるので、目的地そのものは数えません。出発地 = 目的地の場合は 0 です。

### 結果の形（3方式で共通）

`{"path", "hops", "distance", "cost", "expanded"}` の辞書を返します。**到達できない場合は `path` が `None`**（`hops`・`distance`・`cost` も `None`）です。実行時間は `benchmark.py` 側で測ります。

## 9. ヒューリスティック関数

A* が最小移動コストの経路を返すには、h(n) が **許容的（admissible）**、つまり**実際の残りコストを決して超えない**必要があります（さらに、この実装のように確定したノードを再び開かない場合は、**一貫的（consistent）**：道路 u–v について h(u) ≤ cost(u, v) + h(v) であることが必要です）。

### 直線距離はいつ許容的か

**直線距離（ユークリッド距離）が常に許容的とは限りません。** 次の2つの条件がそろうときだけ、目的地までの直線距離を移動コストの**下界**として使えます。

1. **すべての道路で、距離 ≥ 両端ノードの直線距離**（座標と距離データが整合している）
2. **すべての道路で、コスト倍率 ≥ 1**

サンプルネットワークと定義済みのシナリオは、この条件を満たすように作ってあります（`euclidean_lower_bound_violations(network)` が空であることをテストで確認）。このとき直線距離は三角不等式により一貫的にもなります。
**コスト倍率が 1 未満の道路を許す拡張**（例：緊急車両の優先走行で速く走れる道路）では、直線距離が残りコストを超えることがあり、**許容性を考え直す必要があります**。

### ヒューリスティックの効果は場合による

教材作成時の確認では、サンプルの新宿 → 江東で、展開ノード数は h = 0 で 8、直線距離で 4 でした。一方、格子状のネットワークの対角の角から角では、直線距離のヒューリスティックはほとんど効きませんでした（899 → 894）。**A* が常に Dijkstra 法より大きく速いとは限りません**。なぜそうなるのかを考察してください。

## 10. 理論計算量の比較

ノード数を **V**、道路数を **E** とします。

| 方法 | 計算量 | 求める経路 |
| --- | --- | --- |
| BFS | 隣接リストと FIFO キューで **O(V + E)** | 最小ホップ数 |
| Dijkstra 法 | 隣接リストと二分ヒープで、典型的には **O((V + E) log V)** | 最小移動コスト |
| A* | ヒューリスティックの質と、展開するノード数に依存する | 最小移動コスト（h が許容的・一貫的なら） |

- Dijkstra 法の計算量は実装方式で変わります。例えば、ヒープを使わず毎回すべてのノードから最小を探すと O(V²)、この教材のように「古い候補をキューに残す」方式では、キューの要素数が最大で O(E) になるので O(E log E)（= O(E log V)）と書くこともあります。
- **A* は、h(n) = 0 なら Dijkstra 法と同じ探索**です。適切なヒューリスティックで探索範囲を減らせる場合がありますが、**常に Dijkstra 法より速いとは断定できません**（h の計算自体にも時間がかかります）。
- この実装の `adjacency()` は呼び出すたびに隣接リストを作り直すので、探索1回ごとに O(V + E) の前処理が含まれます。測定のときは注意しましょう。

### 道路閉鎖と探索時間

道路閉鎖で探索できる道路が減ると、探索が速く終わるように思えます。しかし、

- 目的地への近道が閉鎖されると、**遠回りの代替経路**を探すために、より多くのノードを展開することがある
- 到達できない場合、出発地から行けるノードを**すべて調べ尽くしてから**「到達不能」と判定する

ため、**道路閉鎖率と探索時間の関係は、単純な単調増加とは限りません**。閉鎖率が高く、出発地の周りが小さく分断された場合は、むしろ短時間で終わることもあります。

Big-O は漸近的な評価であり、実測時間そのものではありません。

| `textbook/fixed_queue.py`（第4章 `chap04/fixed_queue.py`） | 固定長キュー `FixedQueue`（リングバッファ）。`enque`・`deque`・`is_empty`、満杯で `FixedQueue.Full`、空で `FixedQueue.Empty` の例外 | `routing.bfs()` の FIFO キュー |

- BFS では、各ノードをキューに入れるのは「初めて見つけたとき」の1回だけなので、**容量をノード数 V にすれば満杯になりません**。万一満杯になっても、データが黙って消えるのではなく例外が発生します。
- 教科書のサンプルコードを**そのままコピー**したものです（SHA-256で原本との一致を確認済み）。import しても副作用（表示や入力の待ち受け）はありません。**編集しないでください。**

### 利用しなかったコード

| ファイル | 理由 |
| --- | --- |
| 第4章 `chap04/queue.py`（`Queue`） | `collections.deque(maxlen=...)` を使っており、**満杯のとき例外を出さずに古いデータを黙って捨てる**。BFS の途中で未処理のノードが失われる危険があるため、使用しない（`deque(maxlen=...)` を BFS のキューとして使うのは誤り） |
| 第4章 `chap04/fixed_stack.py`、`stack.py` | BFS・Dijkstra 法・A* では使わない。DFS（深さ優先探索）で到達可能性だけを調べる場合には `fixed_stack.py` が使える（`stack.py` は `queue.py` と同じ理由で注意） |
| 第6章 `chap06/heap_sort.py`、`heap_sort_heapq.py` | ヒープを使ったソート。教科書には優先度付きキューのクラスがないため、Dijkstra 法・A* では Python 標準の `heapq` を使った。`heap_sort_heapq.py` は `heapq.heappush`・`heappop` の使い方の参考になる |

### 参考にした考え方

- **第3章「探索」**：線形探索・二分探索・ハッシュ法。訪問済みノードの管理に使う Python の `dict`・`set` は、ハッシュ表です。
- **第5章「再帰的アルゴリズム」**：経路の復元（親をたどる）や、DFS を再帰で書く場合の参考になります。

## 14. Core Research：必須課題

すべてのチームが取り組む課題です。

1. **道路ネットワークを読み込む。**（`road_network.load_network`）
2. **道路閉鎖シナリオを適用する。**（`disaster.apply_scenario`）
3. **一般車両・緊急車両の通行条件を区別する。**
4. **BFS で経路を探索する。**
5. **Dijkstra 法で経路を探索する。**
6. **A* で経路を探索する。**（h = 0 と、自分たちで実装した直線距離の h）
7. **地震前後の経路を比較する。**（到達可能性、距離・コストの増加、代替経路）
8. **一般車両と緊急車両の経路を比較する。**
9. **展開ノード数を比較する。**
10. **処理時間を比較する。**（`benchmark.py` の TODO）
11. **結果を表・グラフにまとめる。**
12. **理論計算量と実測結果を考察する。**

## 15. Advanced Research：発展課題

必須課題を終えたチームが挑戦する課題です。**Advanced A〜E のうち、チームの能力と時間に応じて1つ以上を選択**してください。すべてを実装する必要はありません。

### Advanced A：災害規模と到達可能性

**目的**：道路閉鎖率が、道路ネットワークの連結性と到達可能性に与える影響を調べる。

1. 道路閉鎖率を段階的に増やす（0%, 10%, 20%, …）。
2. ランダムに閉鎖する道路を選ぶ（`disaster.py` の TODO。**乱数シードを記録**する）。
3. 同じ閉鎖率で複数回試行する。
4. 到達可能な出発地・目的地の組の割合を測定する。
5. 最短経路の移動コストを比較する。
6. ネットワークが分断される条件を調べる（C2 の連結成分の考え方が使えます）。

### Advanced B：緊急車両優先ルート

**目的**：一般車両と緊急車両の通行条件の違いを分析する。

1. 緊急車両専用道路を設定する（割合を変える）。
2. 一般車両の最短経路を求める。
3. 緊急車両の最短経路を求める。
4. 到達可能性を比較する。
5. 移動コストを比較する。
6. 緊急車両優先の規制の効果を考察する（緊急車両は速くなるが、一般車両はどれだけ遠回りになるか）。

> **緊急車両がすべての道路を自由に通行できる、という誤った前提を置かないでください。** 物理的に通行できない（`closed`）道路は、緊急車両も通れません。

### Advanced C：時間とともに変化する道路ネットワーク

**目的**：災害発生後に道路の状態が変化する状況を研究する。

1. 時刻ごとに道路の閉鎖状態を変える。
2. 一部の道路の**復旧**を表す。
3. 新たな道路の閉鎖を表す。
4. 経路を**再探索**する。
5. 再探索前後の経路を比較する。
6. 経路の変更回数と計算コストを評価する。

> 移動中の車両の位置を考える場合（途中まで進んだところで道路が閉鎖される、など）は、単純な**静的最短経路問題**から、**動的経路計画問題**へと変わります。

### Advanced D：実際の東京圏道路データへの拡張

**目的**：架空の道路ネットワークから、実際の道路ネットワークを使った研究へ発展させる。

1. 公開されている道路データの入手方法を調査する。
2. 道路ネットワークをグラフに変換する。
3. ノード数とエッジ数を分析する。
4. 道路閉鎖シナリオを設定する（架空のもの）。
5. BFS・Dijkstra 法・A* を比較する（大規模なネットワークでの違い）。
6. 地域ごとの到達可能性を分析する。

> **OpenStreetMap** などの公開データを使う場合は、**ライセンス（ODbL）と出典の表示方法**を必ず確認してください。
> 実際の道路データを使っても、閉鎖シナリオは架空であり、**実際の災害時の通行可否を示すものではありません**。

### Advanced E：移動距離・所要時間・安全性の多目的最適化

**目的**：最短距離だけでなく、移動時間や危険度を考えた経路探索へ発展させる。

1. 道路ごとに移動時間を設定する。
2. 道路ごとに危険度を設定する（**教育用の仮の値**）。
3. 距離が最小のルートを求める。
4. 時間が最小のルートを求める。
5. 危険度を考えたルートを求める。
6. 複数の評価指標のトレードオフを比較する。

> 重み付き和（例：コスト = a × 距離 + b × 時間 + c × 危険度）を使う場合は、**各指標の単位**と、**重み a, b, c の意味**（何を何倍重視するのか）を明確にしてください。単位の違う量をそのまま足すと、結果の意味が分からなくなります。

## 16. 実験条件と評価指標

### 記録すべき実験条件

- PC 環境（CPU、メモリ）、OS、Python のバージョン
- 道路ネットワーク（V、E、生成方法と乱数シード）
- 災害シナリオ（閉鎖率、緊急車両専用道路の割合、コスト倍率、乱数シード）
- 車両の種類、出発地・目的地
- A* のヒューリスティック
- 測定回数と、平均値・中央値などの集計方法

### 評価指標

| 指標 | 内容 |
| --- | --- |
| 経路の有無 | `path` が `None` かどうか（到達できない場合は別に集計する） |
| ホップ数・総距離・総移動コスト | `hops`、`distance`、`cost` |
| 展開ノード数 | `expanded`（8章の定義） |
| 実行時間 | `time.perf_counter()` で測る（ネットワークの生成・表示は含めない） |
| 到達可能率 | 到達できた出発地・目的地の組の割合 |

### 公平な比較の条件

- **同じ道路ネットワーク・同じ災害シナリオ・同じ車両・同じ出発地と目的地・同じ移動コスト**を使う。
- 乱数を使う場合は**シードを記録**する。
- **到達できない場合は別に集計**する。
- **BFS の最小ホップ数と、Dijkstra 法の最小移動コストを混同しない。**
- **A* の最適性は、Dijkstra 法との比較で検証**する。
