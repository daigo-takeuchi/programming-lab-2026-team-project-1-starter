## 2. 配送ルート最適化とは何か

配送車やドローンは、1つの拠点から出発して多くの配送先を回り、拠点に戻ってきます。
同じ配送先を回る場合でも、**回る順番**によって総移動距離は大きく変わります。距離が短いほど、時間・燃料・電力・CO₂ 排出を減らせます。

Core Research では、問題を次のように単純化します。

- 配送拠点（Depot）は1か所、配送車は1台
- 配送先は **2次元平面上の点**で、地点間の距離は**ユークリッド距離（直線距離）**
- 道路・渋滞・交通規制・車両の積載量・配送時間の指定・バッテリーなどは考えない（Advanced Research で扱う）

## 3. 巡回セールスマン問題（TSP）

この問題は、**巡回セールスマン問題（Traveling Salesperson Problem：TSP）**の基本形です。

> **入力**：地点の集合と、地点間の距離
> **目的**：ある地点から出発し、すべての地点をちょうど1回ずつ訪問して出発点に戻る、総距離が最小の巡回路を求める

TSP は **NP 困難**な問題として知られており、地点数が増えると、最適解を効率よく求める方法は（P ≠ NP なら）存在しないと考えられています。そのため、小さな問題では全探索で最適解を求め、大きな問題では**最近傍法や 2-opt などの近似・局所探索**で、短いルートを現実的な時間で求めます。

この教材の距離は**対称**（A→B と B→A が同じ距離）です。そのため、あるルートとその**逆向きのルート**は同じ総距離になります。

## 4. 配送先と距離の表現

### 地点データ（`locations.py`）

```python
locations = {"Depot": (0, 0), "A": (2, 3), "B": (5, 1), "C": (6, 4), "D": (1, 6), "E": (4, 7)}
depot = "Depot"
```

`validate_locations()` で次を検証し、不正なら `ValueError` にします。

- 配送拠点が存在する
- 座標が2つの数値で、**NaN や無限大ではない**（`True`/`False` も数値として扱わない）
- 地点IDが一意（辞書のキーなので保証される。JSON ファイルの**重複キー**は `load_scenarios()` で検出する。Python の `json` は重複キーを黙って上書きするため）

配送先は「配送拠点以外のすべての地点」です（`delivery_ids()`）。配送先が0件の場合も安全に扱えます（総距離 0）。

### ルートの表し方（すべてのアルゴリズムで共通）

```python
route = ["A", "D", "E", "C", "B"]     # 配送先IDを訪問する順に並べたリスト
```

**配送拠点はリストに含めません。** 総距離を計算するときに、出発点・帰着点として前後に付け足します。

```text
Depot → A → D → E → C → B → Depot
```

こうすることで、すべてのアルゴリズムで**同じ距離計算関数**を使えます。

### 距離の計算（`distance.py`）

| 関数 | 内容 |
| --- | --- |
| `distance(locations, a, b)` | 2地点間のユークリッド距離 √((xa − xb)² + (ya − yb)²)（`math.hypot`） |
| `route_distance(locations, depot, route)` | 総距離：配送拠点 → route の順 → 配送拠点（**帰着の距離も含む**） |
| `check_route(locations, depot, route)` | ルートの検証：存在しないID・配送拠点・重複がなく、すべての配送先を含む |
| `format_route(depot, route)` | 表示用の文字列 |

### サンプルデータ（`data/sample_deliveries.json`）

| シナリオ | 配送先数 | 特徴 |
| --- | ---: | --- |
| Town 1 | 5 | 配送拠点の周りに配送先がある。**最近傍法が最適解を見つける** |
| Town 2 | 6 | 配送拠点の北と南に配送先がある。**最近傍法が最適解を見つけられない**（全探索で確認済み。最適解との差 25.2%） |

どちらのシナリオも、最適なルートは「1つのルートとその逆向き」の2通りだけです（全探索で確認済み）。

## 5. ランダム探索（`solvers.random_search`）

配送先の訪問順をランダムに `trials` 個作り、**最も短いルート**を返します（`random.sample()`）。

```python
solvers.random_search(locations, depot, trials=20, seed=0)
```

- `seed` を指定すると、同じ結果を再現できます。
- `evaluated` に試行回数を記録します。
- **同じルートが何度も生成されることがあります**（重複を取り除いていない）。そのため、N! 回試行しても、すべてのルートを調べられるとは限りません。
- 試行回数を増やすほど良いルートが見つかりやすくなりますが、**最適解の保証はありません**。試行ごとの結果のばらつきも評価しましょう。

## 6. 最近傍法（`solvers.nearest_neighbor`）

**今いる地点から最も近い未訪問の配送先**へ移動することを繰り返します。

1. 配送拠点から出発する。
2. 未訪問の配送先の中で、**今いる地点から最も近い**ものを選ぶ（同じ距離なら **ID の小さい方**）。
3. その地点へ移動する。
4. すべての配送先を訪問するまで繰り返し、最後に配送拠点へ戻る。

### Town 2 で最近傍法が最適解を見つけられない理由

```text
最近傍法：Depot → B → C → E → F → D → A → Depot   総距離 52.439
最適解  ：Depot → B → A → C → E → F → D → Depot   総距離 41.871
```

最近傍法は、南の B → C → E と近い順に進み、北の F → D へ移動したあと、**南西に残しておいた A** へ戻らなければなりません。D (2, 8) から A (−3, −8) へは約 16.8、A から配送拠点へは約 8.5 と、最後に長い移動が発生します。
最適解は、南にいる間に A も回ってから北へ向かいます。**「その時点で一番近い」選択を続けても、全体として最短になるとは限らない**のが、最近傍法（貪欲法）の特徴です。

> 試行20回のランダム探索（50.076）の方が、最近傍法（52.439）より短いルートを見つけることもあります（`starter.py` の結果）。

## 7. 全探索（`solvers.brute_force`）

**すべての訪問順**（N! 通り、`itertools.permutations`）の総距離を計算し、最短のルートを返します。

- 全探索は、小規模な問題の**最適解を求めるための基準**です。**最後まで完了した場合だけ**、その結果を**厳密な最適解**として扱えます。
- 配送先数が上限 `MAX_BRUTE_FORCE = 8`（8! = 40,320 通り）を超える場合は、時間がかかりすぎるので `ValueError` にします（`max_deliveries` 引数で変更できますが、N を1増やすごとに候補が約 N 倍になることに注意）。
- 同じ距離のルートが複数あれば、列挙した順で最初のもの（ID の辞書順）を返します。
- この実装では、**逆向きのルートも別の候補として数えています**（対称な TSP では同じ距離になるので、本当は半分で済む）。

### 解の品質

全探索の最適距離を **OPT** とすると、

```text
最適解との差（Optimality Gap, %） = (アルゴリズムの距離 − OPT) / OPT × 100
```

`solvers.optimality_gap(value, optimum)` は、**OPT が 0 のとき**（配送先が0件、またはすべて配送拠点と同じ位置）は比が定義できないので **`None`** を返します。

### `starter.py` の結果

| シナリオ | 方法 | 総距離 | 最適解との差 | 評価した候補ルート数 |
| --- | --- | ---: | ---: | ---: |
| Town 1 | Random（20回、seed=0） | 23.224 | 6.5% | 20 |
| Town 1 | Nearest Neighbor | 21.797 | 0.0% | 1 |
| Town 1 | Brute Force | 21.797 | 0.0% | 120 |
| Town 2 | Random（20回、seed=0） | 50.076 | 19.6% | 20 |
| Town 2 | Nearest Neighbor | 52.439 | 25.2% | 1 |
| Town 2 | Brute Force | 41.871 | 0.0% | 720 |

## 8. 2-opt（`two_opt.py`：学生の実装課題）

### 基本原理

2-opt は、ルートの中の**2本の辺（移動区間）を取り除き、つなぎ方を変える**ことで、ルートを短くする**局所探索**アルゴリズムです。訪問順のリストで見ると、**ルートの一部分を逆順にする**操作に当たります。

```text
変更前：Depot → A → [B → C] → D → Depot
変更後：Depot → A → [C → B] → D → Depot

取り除いた辺：A–B と C–D
新しい辺    ：A–C と B–D
```

特に、ルートが**交差している**場合、交差している部分を反転すると必ず短くなります（三角不等式による）。

部分反転の関数 `reverse_segment(route, i, j)` は用意してあります（i 番目から j 番目までを両端を含めて反転した**新しいリスト**を返す）。

### 実装の手順

```python
def two_opt(route, locations, depot):
    # TODO: 学生が実装する
    raise NotImplementedError
```

1. 初期ルートを用意する（最近傍法やランダム探索の結果）。
2. すべての (i, j)（i < j）について、`reverse_segment(route, i, j)` で**候補ルート**を作る。
3. 候補ルートの総距離を `route_distance()` で計算する。
4. 今のルートより**短くなれば更新**する。
5. どの候補でも**改善しなくなるまで**繰り返す。

戻り値は `solvers.py` の関数にそろえて `{"route", "distance", "evaluated"}` にすると、比較しやすくなります。
`tests/test_two_opt.py` の `TestTwoOpt` は、`two_opt()` が未実装の間はスキップされ、実装すると自動的に実行されます（改善後も正しいルートか、距離が初期ルート以下・最適解以上か、を確認）。

### 初期ルートの比較

次の2つの初期ルートから 2-opt を行い、結果を比べてください。

- **ランダムに生成したルート**
- **最近傍法で生成したルート**

2-opt は「今のルートの近く」だけを探すので、**初期ルートによって最終結果が変わる**ことがあります。

### 2-opt の注意点

- 2-opt は**局所探索**です。「どの2本の辺をつなぎ替えても短くならない」状態（**局所最適解**）で止まりますが、それが**大域的な最適解（全探索の結果）とは限りません**。
- 実行時間は、候補ルートの評価方法（総距離を毎回計算するか、差分だけ計算するか）、改善戦略（最初に見つけた改善を採用するか、最も良い改善を採用するか）、反復回数によって変わります。
- **「2-opt の計算量は O(N²)」と単純に言うことはできません**（9章）。

## 9. 理論計算量の比較

配送先数を **N**、ランダム探索の試行回数を **T** とします。

| 方法 | 計算量の目安 | 解の品質 |
| --- | --- | --- |
| ランダム探索 | 1ルートの生成と評価が O(N) → 全体で **O(TN)** | 保証なし |
| 最近傍法 | 各ステップで未訪問の地点をすべて調べる → **O(N²)** | 保証なし（最適解より長くなることがある） |
| 全探索 | N! 通りのルートを、それぞれ O(N) で評価 → **O(N! × N)** | **最適解**（完了した場合） |
| 2-opt | 1回の近傍探索で調べる候補は **O(N²)** 個（下を参照） | 局所最適解 |

### 全探索の候補ルート数

| N | N! |
| ---: | ---: |
| 5 | 120 |
| 6 | 720 |
| 8 | 40,320 |
| 10 | 3,628,800 |
| 15 | 1,307,674,368,000 |
| 20 | 2,432,902,008,176,640,000 |

N = 20 では約 2.4 × 10¹⁸ 通りで、1秒に100万ルート調べても約7万7千年かかります。
対称な TSP では、逆向きのルートが同じ距離になるので候補を半分に、さらに出発点を固定すれば (N − 1)!/2 程度に減らせますが、**階乗的に増えることに変わりはありません**。

### 2-opt の計算量

- **1回の近傍探索**で調べる候補（i, j の組）は **O(N²)** 個です。
- 各候補の総距離を**最初から計算し直す**と1候補あたり O(N) かかるので、1回の近傍探索は **O(N³)** 程度になります。
- 反転で変わるのは2本の辺だけなので、**距離の差分**（取り除く2辺と新しい2辺の長さの差）を計算すれば、各候補の改善量を **O(1)** で評価できます。このとき1回の近傍探索は O(N²) です。
- ただし、**改善を何回繰り返すか**は問題によって異なります。アルゴリズム全体の計算量を単純に O(N²) とは言えません。**1回の近傍探索のコスト**と**全体の実行時間**を区別して測定・考察してください。

Big-O は漸近的な評価であり、実測時間そのものではありません。

## 13. Core Research：必須課題

すべてのチームが取り組む課題です。

1. **配送先データを読み込む。**（`locations.load_scenarios`）
2. **距離を計算する。**（帰着の距離を含めた総距離）
3. **ランダム探索を実行する。**
4. **最近傍法を実行する。** 訪問の過程を追って説明する。
5. **全探索を実行する。**
6. **3方式の結果を比較する。**
7. **2-opt の基本原理を理解する。**（部分反転と、2本の辺のつなぎ替えの関係）
8. **2-opt による改善を実装する。**（`two_opt.py`。詳しい評価は Advanced A）
9. **配送先数 N を変更して実験する。**（`benchmark.make_locations` を使う）
10. **最適解との差を比較する。**
11. **結果を表・グラフにまとめる。**
12. **理論計算量と実測結果を考察する。**

## 14. Advanced Research：発展課題

必須課題を終えたチームが挑戦する課題です。**Advanced A〜E のうち、チームの能力と時間に応じて1つ以上を選択**してください。すべてを実装する必要はありません。
2-opt は Core Research の実装課題（Core 8）でもあり、Advanced A では改善性能をより詳しく研究します。

### Advanced A：2-opt の実装と改善効果

**目的**：局所探索によって配送ルートを改善する。

1. 2-opt を実装する。
2. ランダムな初期ルートを改善する。
3. 最近傍法のルートを改善する。
4. 改善前後の総距離を比較する。
5. **改善率** = (改善前の距離 − 改善後の距離) / 改善前の距離 を計算する。
6. 最適解との差を比較する。
7. 初期ルートによる結果の違いを分析する（同じデータで、ランダムな初期ルートを何通りも試す）。

発展的には、距離の差分による O(1) の評価、「最初に見つけた改善」と「最も良い改善」の比較、Or-opt や 3-opt なども調べてみましょう。

### Advanced B：配送先数と探索空間の増大

**目的**：TSP の計算困難性を実験的に理解する。

1. 配送先数 N を変更する。
2. 全探索の候補ルート数（N!）を計算する。
3. 全探索の処理時間を測定する（**安全な実行上限**を必ず設ける）。
4. 最近傍法と比較する。
5. ランダム探索と比較する。
6. 2-opt を追加して比較する。
7. 理論計算量と実測結果を比較する。

### Advanced C：道路ネットワーク上の配送ルート

**目的**：直線距離による TSP から、道路ネットワークを使ったルート最適化へ発展させる。

1. 道路をグラフとして表す。
2. 交差点をノードとする。
3. 道路を**重み付きの辺**（道路の長さ）として表す。
4. **Dijkstra 法**で2地点間の最短経路を求める。
5. 配送先どうしの**道路距離**を計算する。
6. 直線距離を使った TSP と比べる（同じ訪問順でも、道路距離では総距離や最適な順序が変わることがある）。

実際の地図 API は使わず、**架空の道路ネットワーク**を使ってください。道路が一方通行の場合、距離が非対称（A→B と B→A が違う）になることにも注意しましょう。

### Advanced D：ドローン配送とエネルギー制約

**目的**：配送距離だけでなく、ドローンのエネルギー消費を考える。

1. 飛行距離に応じた消費エネルギーを設定する。
2. バッテリー容量を設定する。
3. 配送する荷物の重量を設定する（荷物を降ろすと機体が軽くなり、消費エネルギーが変わる）。
4. エネルギー制約を満たすルートを探索する。
5. 最短距離のルートと、省エネルギーのルートを比較する。
6. 充電地点の追加を検討する。

> 実機の飛行制御は行わず、**シミュレーションに限定**してください。

### Advanced E：複数車両・配送容量・時間制約

**目的**：TSP を **Vehicle Routing Problem（VRP：配送計画問題）**へ発展させる。

1. 複数の配送車両を設定する。
2. 各車両の配送容量（積載量）を設定する。
3. 配送先ごとの荷物量を設定する。
4. 車両への配送先の割り当てを考える。
5. 配送時間帯の制約を追加する。
6. 総移動距離と配送効率を比較する。

> **単一車両の TSP と、複数車両の VRP は異なる最適化問題です。** VRP では「どの配送先をどの車両が担当するか（割り当て）」と「各車両がどの順に回るか（ルート）」を同時に決める必要があり、TSP の解法をそのまま使うことはできません。

## 15. 実験条件と評価指標

### 記録すべき実験条件

- PC 環境（CPU、メモリ）、OS、Python のバージョン
- 配送先数 N、座標の範囲、データ生成に使った乱数シード
- ランダム探索の試行回数と乱数シード
- 2-opt の初期ルートと改善戦略
- 測定回数と、平均値・中央値・標準偏差などの集計方法

### 評価指標

| 指標 | 内容 |
| --- | --- |
| 総移動距離 | `route_distance()`（全方式で同じ関数） |
| 最適解との差 | `optimality_gap()`（全探索が完了した場合だけ） |
| 実行時間 | `time.perf_counter()` で測る（データ生成・表示は含めない） |
| 評価した候補ルート数 | `evaluated` |
| ランダム探索のばらつき | seed を変えたときの平均・標準偏差・最小・最大 |
| 2-opt の改善率 | (改善前 − 改善後) / 改善前 |

### 公平な比較の条件

- **同じ配送先データ・同じ距離計算関数・同じ出発・帰着地点**を使う。
- **乱数シードを記録**し、ランダム探索は**複数回試行**する。
- **実行時間と解の品質を分けて**評価する。
- **全探索が完了した場合だけ**、最適解との差を計算する。
