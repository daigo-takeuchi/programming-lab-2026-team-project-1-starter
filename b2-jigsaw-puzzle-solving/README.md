## 1. 研究テーマと目的

**B2：ジグソーパズルの解法と計算量**

ジグソーパズルを題材に、**組合せ爆発・全探索・バックトラッキング・貪欲法・制約充足問題（CSP）**の考え方を学びます。

| | 問い |
| --- | --- |
| RQ1 | **ピース数と探索空間**：ピース数 N が増えると、配置の組合せ数と計算量はどう変化するか。制約（辺の整合性・外周）は探索空間をどれだけ減らすか。 |
| RQ2 | **解法アルゴリズムの比較**：全探索・バックトラッキング・貪欲法は、解が見つかるか・正確か・速いか・どれだけ探索するか、でどう違うか。 |

学習段階に応じて、課題を2層に分けています。

- **Core Research（必須課題）**：候補配置数の分析、全探索の確認、バックトラッキングと貪欲法の実装・比較
- **Advanced Research（発展課題）**：組合せ爆発の定量化、CSP としての定式化、探索の改善、画像を使った復元

このリポジトリには、**全探索だけ**が実装されています。バックトラッキングと貪欲法は、関数の入口と TODO だけを用意しているので、チームで実装してください。

## 2. ジグソーパズルと探索問題

ジグソーパズルを解くことは、「どの位置にどのピースを置くか」の組合せの中から、**すべての制約を満たす配置**を探す問題です。

- **候補**：ピースの並べ方（N 個のピースなら N! 通り）
- **制約**：隣り合う辺がかみ合うこと、外周の辺が平らであること、各ピースを1回だけ使うこと
- **解**：すべての制約を満たす配置

このように「変数（各位置）に値（ピース）を割り当て、制約をすべて満たす組合せを探す」問題を、**制約充足問題（CSP：Constraint Satisfaction Problem）**と呼びます。

ピース数が増えると候補の数は爆発的に増えます（**組合せ爆発**）。そのため、全部を調べるのではなく、**制約を使って調べる範囲を減らす工夫**が重要になります。

## 3. ピースの表現方法

画像認識を必要としない、**エッジ情報付きピースモデル**を使います（`puzzle.py`）。

```python
piece = {"id": 0, "top": 0, "right": 2, "bottom": -3, "left": 0}
```

| ルール | 内容 |
| --- | --- |
| 外周の辺 | `0` は外周の平らな辺。外周に面した辺は必ず 0 |
| 辺の接続 | 隣り合う2辺は、**絶対値が等しく符号が逆**なら接続できる（例：`2` と `-2`）。0 どうしは接続できない |
| ピースの使用 | 各ピースはちょうど1回だけ使う |
| 回転 | Core Research では回転しない（Advanced で拡張） |

**ボード（配置）**は、左上から行優先の順に、各位置に置いたピースの id を並べたリストで表します。まだ置いていない位置は `None` です。

```text
2×2 のボードの位置    board = [2, 0, 3, 1] の意味
   0  1                 ピース2  ピース0
   2  3                 ピース3  ピース1
```

> ⚠️ これは、実際のジグソーパズルの**形状や画像を単純化したモデル**です。実物のピースは、凹凸の形がぴったり一致するかどうかや、絵柄のつながりで判断しますが、このモデルでは整数の一致だけで判断します。

### `puzzle.py` の主な関数

| 関数 | 内容 |
| --- | --- |
| `make_piece(id, top, right, bottom, left)` | ピースを作る |
| `edges_match(a, b)` | 2つの辺が接続できるか |
| `border_ok(piece, row, col, rows, cols)` | 外周条件を満たすか |
| `fits(puzzle, board, index, piece_id)` | その位置にそのピースを置けるか（外周条件と、置いてあるピースとの整合性）。バックトラッキングや貪欲法で使える |
| `is_solved(puzzle, board)` | 完成状態の正解判定（不足・重複・外周・すべての隣接辺を検査） |
| `format_pieces(puzzle)` / `format_board(puzzle, board)` | 表示用の文字列にする |
| `rotate_piece(piece, times)` | TODO（Advanced）：回転 |

### サンプル問題

| 問題 | サイズ | 内容 |
| --- | --- | --- |
| `puzzle_a()` | 2×2、4ピース | 簡単な問題。正しい配置はちょうど1つ。全探索ですぐ解ける |
| `puzzle_b()` | 2×4、8ピース | **貪欲法が失敗し得る問題**。正しい配置はちょうど1つ |
| `puzzle_unsolvable()` | 2×2、4ピース | 解が存在しない問題（Puzzle A の1辺を変えたもの） |

#### Puzzle B：貪欲法が失敗し得る問題

```text
正解の配置：  4 5 1 6
             0 7 3 2
```

上段の2番目・3番目に入るピース 5 と 1 は、どちらも「上が平ら、左が -1」です。位置 1 には**どちらも置けるように見えます**が、ピース 1 を置くと、位置 2 に置けるピースがなくなります。

「行優先の順に、置けるピースのうち id が最小のものを選ぶ」貪欲法や、「すでに置いたピースと一致する辺の数が最大のものを選び、同点なら id が最小のもの」を選ぶ貪欲法は、位置 1 でピース 1 を選んで**行き詰まります**（教材作成時に確認済み）。正しく解くには、過去の選択を取り消して別の候補を試す**バックトラッキング**が必要です。

> **なぜ 2×2 や 2×3 ではないのか？**
> 2×2 や 2×3 のパズルでは、どのピースも「どの辺が平らか（0か）」の組合せが互いに異なります（左上の角、上辺の中央、…）。そのため、外周条件を確認すれば、**各位置に置けるピースは1つに決まり**、貪欲法が失敗することはありません。
> 2×4 では上辺の中央が2か所あり、同じ種類のピースが2つになるため、初めて「どちらを選ぶか」の迷いが生じます。
> ただし、貪欲法が失敗するかどうかは**評価関数と同点時の選び方に依存**します（例えば id が最大のものを選ぶと Puzzle B は解けてしまいます）。

## 4. ピース数と探索空間

### 候補配置数（`complexity.py`）

| | 式 | 意味 |
| --- | --- | --- |
| 回転なし | **N!** | N 個の異なるピースを N 個の位置に並べる方法の数 |
| 回転あり | **N! × 4^N** | さらに各ピースの4方向の回転を区別した場合の上限 |

| N | 例 | N!（回転なし） | N! × 4^N（回転あり） |
| ---: | --- | ---: | ---: |
| 4 | 2×2 | 24 | 6,144 |
| 6 | 2×3 | 720 | 2,949,120 |
| 9 | 3×3 | 362,880 | 95,126,814,720 |
| 12 | 3×4 | 479,001,600 | 8,036,313,307,545,600 |
| 16 | 4×4 | 20,922,789,888,000 | 89,862,698,310,039,502,848,000 |

- これらは**制約を無視した候補配置数**であり、**合法な完成状態の数ではありません**。
- 回転ありの場合、対称なピース（例：4辺が同じ形）や同一視できる配置があると、異なる実状態の数はこれより少なくなります。

### 制約による探索空間の削減

- **外周の制約**：R×C のボードでは、角が4か所、辺（角以外の外周）が 2(R−2)+2(C−2) か所、内側が (R−2)(C−2) か所です。平らな辺の数でピースを分類すると、各位置の候補が大きく減ります。
- **隣接する辺の整合性**：すでに置いたピースとかみ合わない候補は、その先を調べる必要がありません（バックトラッキングの枝刈り）。

### 計算量

| 方法 | 計算量の目安 |
| --- | --- |
| 全探索（回転なし） | 候補配置数は **O(N!)** |
| 全探索（回転あり） | 候補配置数は **O(N! × 4^N)** |
| バックトラッキング | 最悪の場合は指数的・階乗的な探索になり得るが、**制約によって枝を削減できる** |
| 貪欲法 | 候補の評価方法によって変わるが、各位置で候補を1つ選ぶだけなので、全探索よりずっと少ない候補で終了することが多い（ただし正しい解が得られるとは限らない） |

> **候補配置数と実行時間の計算量は区別してください。**
> 全探索で、1つの完全配置の正当性を `is_solved()` で O(N) かけて検査する単純な実装では、総実行時間は **O(N × N!)** になり得ます。

## 5. 全探索・バックトラッキング・貪欲法

| | 全探索 | バックトラッキング | 貪欲法 |
| --- | --- | --- | --- |
| 考え方 | すべての並べ方を作り、1つずつ完成判定する | 1つずつ置き、矛盾したら戻って別の候補を試す | 各位置で局所的に最も良い候補を選び、戻らない |
| 解の存在判定 | 探索を完了できれば可能 | 探索を完了できれば可能 | **できない**（失敗しても解がないとは限らない） |
| 解の正確性 | 見つかった解は正しい | 見つかった解は正しい | 完成した場合のみ正しい。途中で行き詰まることがある |
| 速さ | 遅い（N! 通り） | 制約が強いほど速い | 速い |
| このリポジトリ | ✅ 実装済み | TODO（Core 3） | TODO（Core 4） |

### 全探索（`solvers.brute_force`）

1. `itertools.permutations` で、ピースの並べ方（順列）を1つずつ作る。
2. その並べ方をボードとして `is_solved()` で完成判定する。
3. 正しければ、その配置を返す。
4. 調べた候補の数が `max_candidates` に達したら、`"limit"`（**探索上限に到達**）として打ち切る。
   これは「解なし」ではありません。すべて調べて解がなかったときだけ `"no_solution"` になります。

### バックトラッキング（`solvers.backtracking`：学生が実装）

1. 位置 0 から順に、ピースを**1つずつ**置いていく。
2. 置いたピースが外周条件や隣のピースと**矛盾したら、その枝を打ち切る**（その先は調べない）。
3. 次の位置に置ける候補がなくなったら、**1つ前に戻って別の候補を試す**。
4. 最後の位置まで置けたら完成。

**再帰**を使うと自然に書けます（「位置 i に置く関数」が、置けたら「位置 i+1 に置く関数」を呼ぶ）。全探索が「最後まで並べてから判定」するのに対し、バックトラッキングは「**途中で判定して早めに諦める**」点が違います。

### 貪欲法（`solvers.greedy`：学生が実装）

1. 位置 0 から順に、その位置に置ける候補を調べる。
2. **局所評価関数**で最も良い候補を1つ選んで置く。選んだピースは再利用しない。
3. 原則として、**過去の選択は戻さない**。
4. 置ける候補がなくなったら `"failed"` として終了する。

局所評価関数の例：すでに置いたピースと一致した辺の数、外周条件を満たすか、同点時の選び方。
**評価関数の選び方によって、解が得られるかどうかが変わります。** Puzzle B で試してみましょう。

## 9. Core Research：必須課題

すべてのチームが取り組む課題です。

1. **ピース数 N と候補配置数 N! の関係を分析する。** 表や対数グラフにまとめる。
2. **全探索の実行結果を確認する。** `starter.py` を実行し、`brute_force()` のコードを読んで説明する。Puzzle B（8! = 40,320 通り）でも試す。
3. **バックトラッキングを実装する。**（`solvers.backtracking`）
4. **貪欲法を実装する。**（`solvers.greedy`。局所評価関数をチームで考案する）
5. **3つの方法の探索時間と探索ノード数を比較する。**
6. **正しい解が得られるか比較する。** 特に Puzzle B で、貪欲法が失敗する様子を確認する。
7. **結果を表・グラフにまとめる。**
8. **理論計算量と実測結果を考察する。**

`starter.py` の末尾に TODO 1〜9 があります。

### 比較実験のルール

- **同じパズル・同じピース集合・同じ回転条件**を使う。
- **同じ探索上限**を使う。
- 解の正確性は、**同じ判定関数 `pz.is_solved()`** で評価する。
- **探索時間と探索ノード数**を記録する。
- 次の3つは**異なる指標**です。何を1回と数えたか、**定義を必ず明記**してください。
  - **完全配置の評価回数**：全部並べ終えた配置を `is_solved()` で判定した回数（全探索の `candidates`）
  - **探索ノード数**：探索木の節点（「位置とピースの組」を試した回数など）の数（バックトラッキング）
  - **局所候補の評価回数**：ある位置で候補ピースを評価関数にかけた回数（貪欲法）

## 10. Advanced Research：発展課題

必須課題を終えたチームが挑戦する課題です。**Advanced A〜D のうち、チームの能力と時間に応じて1つ以上を選択**してください。すべてを実装する必要はありません。

### 回転の扱い（どのテーマでも取り組める拡張）

Core Research では回転なしのモデルを使います。Advanced では、ピースを **90°・180°・270° 回転**できるように拡張してみましょう（`pz.rotate_piece()` を実装し、ボードに「ピースの id と回転数の組」を置く）。

| | 候補配置数 | 2×2 | 3×3 |
| --- | --- | ---: | ---: |
| 回転なし | N! | 24 | 362,880 |
| 回転あり | N! × 4^N | 6,144 | 95,126,814,720 |

回転を入れると、1つの位置に対する候補が最大4倍になり、探索空間は 4^N 倍に増えます。

### Advanced A：ピース数と組合せ爆発

**目的**：ピース数の増加による探索空間の爆発的増大を定量化する。

1. N = 4, 6, 9, 12, 16 について N! を計算する。
2. 回転ありの場合の N! × 4^N を計算する。
3. 候補配置数を**対数スケール**でグラフ化する。
4. **毎秒100万候補**を検査できると仮定し、全探索に要する時間を概算する。
5. ピース数の増加に伴う計算困難性を考察する。

> これらは**制約を無視した仮想的な全探索の評価**であり、実際のソルバーの処理時間を直接予測するものではありません。

### Advanced B：制約充足問題（CSP）としての定式化

**目的**：ジグソーパズルを制約充足問題として理解する。

1. 各位置を**変数**とする。
2. 各変数の**候補ピース（定義域）**を定義する。
3. **同じピースを複数回使えない**制約を導入する。
4. **隣接辺の整合性**制約を導入する。
5. **外周の制約**を導入する。
6. 制約を用いて探索候補を減らす（外周条件で定義域を事前に絞り込む など）。

発展的には、**最小残余値（MRV：候補が最も少ない変数から決める）**や**制約伝播（1つ決めたら隣の候補を減らす）**の導入を検討してください。

### Advanced C：探索アルゴリズムの改善

**目的**：全探索・バックトラッキング・貪欲法の性能を改善する。

1. バックトラッキングの探索順序を変える（行優先、外周から、渦巻き状 など）。
2. 外周ピースから優先的に配置する。
3. 候補ピースを事前に分類する（角・辺・内側、辺の値ごとの索引 など）。
4. 貪欲法の評価関数を改善する。
5. 貪欲法が失敗した場合の再試行を導入する（開始位置や同点時の選び方を変える など）。
6. **ビームサーチ**などの近似探索を調査する。

追加した工夫について、**改善前後の実行時間・探索ノード数・正解率**を比較してください。大きなパズルを自動生成する関数を作ると、実験がしやすくなります（正解の配置から辺の値を決め、ピースをシャッフルする）。

### Advanced D：画像を使ったジグソーパズル復元

**目的**：実際の画像を分割したピースから、元画像を復元する問題へ発展させる。

1. 画像を格子状に分割する。
2. ピースをシャッフルする。
3. 隣接する画像の端の色や画素値を比較する。
4. ピース間の類似度を計算する。
5. 貪欲法やバックトラッキングを使って復元する。
6. 復元結果を正解画像と比較する（正しい位置に置けたピースの割合 など）。

- 画像処理には **Pillow** や **OpenCV** を使ってもかまいません。ただし、追加ライブラリは **Advanced Research でのみ**使用し、Core Research のコードは標準ライブラリだけで動くようにしてください。
- 画像の端の類似度は「似ている度合い」であり、エッジ情報付きモデルのような**完全な接続判定ではありません**。空や壁など単色の領域では似た端が多くなり、**復元結果に誤りが生じる可能性**があります。

## 11. 実験条件と評価指標

### 記録すべき実験条件

- PC 環境（CPU、メモリ）、OS、Python のバージョン
- パズル（サイズ、ピース数、自動生成した場合は乱数シード）、回転の有無
- 探索上限（`max_candidates` など）
- 探索順序・評価関数など、アルゴリズムの設定
- 測定回数と、平均値・中央値などの集計方法

### 評価指標

| 指標 | 内容 |
| --- | --- |
| 解が見つかったか | `status`（`solved` / `no_solution` / `limit` / `failed`） |
| 解の正確性 | `pz.is_solved()` で検証 |
| 実行時間 | `time.perf_counter()` で測定（表示の時間は含めない） |
| 探索ノード数 | 定義を明記（9章参照） |
| 候補配置の評価回数 | 完全配置の評価回数・局所候補の評価回数（定義を明記） |
| 最大保持状態数 | 同時に保持していた途中状態の数（再帰の深さ、スタックの大きさ など） |
| メモリ使用量 | `tracemalloc` などで測定 |
| 問題サイズに対する性能変化 | N を増やしたときの上記の変化 |

### 注意

- `"limit"`（探索上限に到達）と `"no_solution"`（解なし）を区別する。貪欲法の `"failed"` は「解なし」ではない。
- 全探索は N が大きいとすぐに終わらなくなります。**最初は小さい N から**試し、探索上限を必ず設定してください。
- Big-O は漸近的な評価であり、実測時間そのものではありません。
