## 2. ブロックチェーンの基本構造

ブロックチェーンは、データをまとめた**ブロック**を、**前のブロックのハッシュ値**でつないだ列です。

```text
 Genesis Block          Block 1                Block 2
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│ index: 0     │      │ index: 1     │      │ index: 2     │
│ data: ...    │      │ data: ...    │      │ data: ...    │
│ prev: 000... │  ┌──▶│ prev: f11f...│  ┌──▶│ prev: 1680...│
│ hash: f11f...│──┘   │ hash: 1680...│──┘   │ hash: 8b57...│
└──────────────┘      └──────────────┘      └──────────────┘
```

この教材のブロック（`blockchain.py`）は、次の4つの値を持つ辞書です。

```python
{"index": 1, "data": "Alice -> Bob : 10", "previous_hash": "f11f...", "hash": "1680..."}
```

- `hash` は `index`・`data`・`previous_hash` から計算します。
- 最初のブロック（**Genesis Block**）は `index` が 0、`previous_hash` が `"0" × 64` と決めています。

## 3. 暗号学的ハッシュ関数

この教材では Python 標準の `hashlib.sha256`（SHA-256）を使います。どんな長さのデータからも、256 ビット（32 バイト、16進数で64文字）のハッシュ値を計算します。

暗号学的ハッシュ関数には、次のような性質が求められます。

| 性質 | 意味 |
| --- | --- |
| 決定的 | 同じ入力からは、必ず同じハッシュ値が得られる |
| 雪崩効果 | 入力が1文字でも違うと、ハッシュ値はまったく別のものになる |
| 原像計算困難性 | ハッシュ値から元の入力を求めるのは、事実上不可能 |
| 衝突困難性 | 同じハッシュ値になる2つの異なる入力を見つけるのは、事実上不可能 |

> **教科書のハッシュ法とは目的が違います。** 教科書 第3章のハッシュ法（ハッシュテーブル）は、キーから「表のどこに格納するか」を素早く決めるためのもので、ハッシュ値の衝突は起こる前提で処理します。暗号学的ハッシュ関数は、**改ざんの検出**などのために、衝突が事実上見つからないように設計されています（8章）。

### ハッシュの計算方法（シリアライズ）

ブロックのハッシュは、3つの値を**キーの順序を固定した JSON 文字列**にしてから計算します（`blockchain.compute_hash()`）。

```python
json.dumps({"index": 1, "data": "...", "previous_hash": "..."}, sort_keys=True, ...)
```

単純に文字列をつなげると、`index=1, data="23"` と `index=12, data="3"` がどちらも `"123..."` になってしまうような**曖昧さ**が生じます。JSON にすると、値の区切りが明確になります。

## 4. ハッシュチェーンによる改ざん検出

### 検証で確認すること（`blockchain.find_problems()`、`is_valid_chain()`）

1. 各ブロックに**保存された `hash`** が、**再計算した値**と一致する
2. `previous_hash` が、**直前のブロックの `hash`** と一致する
3. `index` が 0, 1, 2, … と**連続**している
4. Genesis Block が**定義済みの形式**に従う

### 改ざん実験（`starter.py` の Demo A）

ブロック2の `data` だけを書き換えると、ブロック2の**保存された `hash` と再計算した値が一致しなくなり**、改ざんが検出されます。
改ざん実験には `blockchain.tamper_data()` で作った**コピー**を使い、元の正常なチェーンは変更しません。

改ざんした人がブロック2の `hash` も計算し直すと、今度はブロック3の `previous_hash` と一致しなくなります。**1つのブロックの変更は、後続のすべてのブロックに影響する**のがハッシュチェーンの特徴です。

### ⚠️ ハッシュチェーンだけでは改ざんを防げない

ところが、改ざんした人が、**改ざんしたブロックから最後までのハッシュ値をすべて計算し直す**と、チェーンの内部はまた整合した状態になり、`find_problems()` では**改ざんを検出できません**。SHA-256 の計算は速いので、この教材の規模なら一瞬でできてしまいます。

つまり、内部の整合性チェックが意味を持つのは、**信頼できる外部の基準**（例：正しい Genesis Block や、最新ブロックの正しいハッシュ値を、別の信頼できる経路で知っていること）がある場合だけです。

実用のブロックチェーンは、さらに次のような仕組みを組み合わせて改ざんを困難にしています（Advanced E）。

- **分散合意**：多数の参加者が同じ履歴を持ち、どの履歴を正しいとするかを合意する
- **Proof of Work / Proof of Stake**：ブロックを作るのにコスト（計算や預け入れ）を必要とし、履歴の書き換えを割に合わなくする
- **電子署名**：取引を行えるのが、正しい鍵を持つ本人だけであることを保証する

## 5. Merkle Tree の構造

**Merkle Tree（ハッシュ木）**は、各データのハッシュ値を**葉**とし、隣り合う2つのハッシュ値から**親**のハッシュ値を計算していく**二分木**です。

```text
                 Root
                /    \
              H01    H23
             /  \    /  \
            H0  H1  H2  H3
            |   |   |   |
            A   B   C   D
```

### ハッシュの計算規則（`merkle_tree.py`）

```python
leaf_hash   = sha256(b"\x00" + データのバイト列).digest()          # 葉
parent_hash = sha256(b"\x01" + 左の子のハッシュ + 右の子のハッシュ).digest()   # 内部ノード
```

- 葉と内部ノードで**異なる接頭辞**（`0x00` と `0x01`）を付けて、両者を区別します（Certificate Transparency の RFC 6962 と同じ方法）。接頭辞がないと、内部ノードのハッシュを「葉」と偽る攻撃が考えられます。
- ハッシュ値は内部では `bytes`（32 バイト）で扱い、表示するときに16進数にします。
- 文字列のデータは UTF-8 でバイト列にします。

### 木の表し方

`build_tree(data_list)` は、**階層のリスト**を返します。

```python
levels = build_tree(["A", "B", "C", "D"])
levels[0]   # [H0, H1, H2, H3]   葉
levels[1]   # [H01, H23]
levels[2]   # [Root]
```

### Core Research の対象

Core Research では、データ件数 N が **2 のべき乗（1, 2, 4, 8, …）**の場合だけを扱います。それ以外の N（例：3、6）は `ValueError` になります（黙って受け入れません）。2 のべき乗でない場合の処理は Advanced D の課題です。

## 6. Merkle Root と Merkle Proof

### Merkle Root

木の一番上のハッシュ値が **Merkle Root** です。どのデータを1文字変えても、データの順序を入れ替えても、Root は別の値になります。
実用のブロックチェーンでは、ブロックに含まれる取引全体の Merkle Root をブロックのヘッダーに入れておくことで、32 バイトの値1つで全取引を代表させています。

### Merkle Proof：「データ C が含まれている」ことを少ないデータで示す

信頼できる Merkle Root を知っている人に、「データ C がこの木に含まれている」ことを示したいとします。

- **全件検証**：A, B, C, D をすべて渡し、Root を計算し直してもらう → N 件のデータと 2N − 1 回のハッシュ計算が必要
- **Merkle Proof**：C と、C から Root までの経路の**兄弟ノードのハッシュ値**（下図の H3 と H01）だけを渡す

```text
                 Root  ← 計算結果が、信頼できる Root と一致すれば OK
                /    \
           [H01]     H23  ← H23 = parent_hash(H2, H3) を計算
                     /  \
                   H2   [H3]   ← H2 = leaf_hash(C) を計算
                   |
                   C

  Proof = [(H3, 右側), (H01, 左側)]    [ ] が Proof として受け取る兄弟ハッシュ
```

検証する側は、`leaf_hash(C)` → `parent_hash(H2, H3)` → `parent_hash(H01, H23)` と計算し、結果が Root と一致すれば「C は含まれている」と判断できます。必要な兄弟ハッシュは **log₂N 個**（N = 4 なら 2 個、N = 1,048,576 でも 20 個）です。

### Proof に必要な情報

- **兄弟ハッシュの値**だけでなく、それが**左右どちら側にあるか**の情報も必要です。`parent_hash(左, 右)` は順序で値が変わるからです。
- 兄弟ハッシュは、**葉に近い順**に並べると検証しやすくなります。
- **信頼できる Merkle Root がすでに手元にあること**が前提です。Root そのものを Proof と一緒に偽物とすり替えられたら、この検証には意味がありません。

### 実装のヒント（`generate_proof`、`verify_proof` は学生の課題）

- 葉の位置を `index` とすると、各階層での兄弟の位置は、`index` が偶数（左の子）なら `index + 1`、奇数（右の子）なら `index − 1` です。
- 1つ上の階層での自分の位置は `index // 2` です。
- `build_tree()` が返す `levels` を、`levels[0]` から `levels[-2]` まで順に上がっていきます。
- Proof の形はチームで設計してください（例：`[(兄弟のハッシュ, "left" または "right"), ...]`）。
- 正しいデータの Proof が受理されるだけでなく、**改ざんしたデータ**や**別の位置の Proof** が**拒否される**ことも確認してください。`tests/test_merkle_tree.py` の `TestMerkleProof` は、未実装の間はスキップされ、実装すると自動的に実行されます。

## 7. 計算量の比較

N はデータ件数（葉の数）、B はブロック数です。`complexity.py` で理論値を計算できます。

### Merkle Tree（N が 2 のべき乗の完全二分木）

| 項目 | 値 | 関数 |
| --- | --- | --- |
| 葉ノード数 | N | `leaf_count(n)` |
| 内部ノード数 | N − 1 | `internal_node_count(n)` |
| 合計ノード数 | 2N − 1 | `total_node_count(n)` |
| 木の高さ | log₂N | `tree_height(n)` |
| Proof の兄弟ハッシュ数 | log₂N | `proof_length(n)` |

### 処理ごとのハッシュ演算回数

| 処理 | ハッシュ演算回数 | 計算量 | 前提 |
| --- | --- | --- | --- |
| 全データのハッシュ計算 | N | O(N) | 全データが手元にある |
| Merkle Tree の構築（全件から Root を再計算） | 2N − 1 | **O(N)** | 全データが手元にある |
| 既存の木からの Proof 生成 | 0（読み出すだけ） | **O(log N)**（読み出す兄弟の数） | 木の全階層を保持している |
| Proof の検証 | 1 + log₂N | **O(log N)** | 信頼できる Root がある |
| 既存の木の葉を1つ更新 | 1 + log₂N | **O(log N)** | 木の全階層を保持している |
| ハッシュチェーン全体の検証 | B | **O(B)** | — |
| 位置 k のブロック変更後の再計算 | B − k | O(B − k) | 位置 k 以降をすべて計算し直す |

| N | 全件から Root を再計算 | Proof の検証 | 兄弟ハッシュ（32 バイト） |
| ---: | ---: | ---: | ---: |
| 4 | 7 回 | 3 回 | 2 個（64 バイト） |
| 1,024 | 2,047 回 | 11 回 | 10 個（320 バイト） |
| 1,048,576 | 2,097,151 回 | 21 回 | 20 個（640 バイト） |

### 計算量比較の注意

- **Proof の検証が O(log N) であることは、木の構築も O(log N) であることを意味しません。** 木を作るには、すべての葉を計算するので O(N) です。Proof の生成・葉の更新が O(log N) で済むのは、**作った木の階層を保持している場合**です。
- 「全件を受け取って Root を作り直す」方法と、「既知の Root に対して Proof で1件を検証する」方法は、**前提と検証対象が違います**。後者は Root と Proof を信頼できる経路で得ていることが前提で、確かめられるのは「その1件が含まれていること」だけです。
- ここでの O 記法は**ハッシュ演算の回数**を数えたものです。1回のハッシュ計算にかかる時間は**データのバイト長に比例**するので、大きなデータを扱う場合は別に考える必要があります。

## 11. Core Research：必須課題

すべてのチームが取り組む課題です。

1. **簡易ブロックチェーンを実行する。**（`starter.py` の Demo A）
2. **ハッシュ値によるブロックの連結を理解する。** `previous_hash` と `hash` の関係を図にする。
3. **データ改ざんによるハッシュ不一致を確認する。** 改ざん位置を変えたり、改ざんしたブロックの `hash` だけを計算し直したりして、検出結果がどう変わるか調べる。
4. **Merkle Tree を構築する。**（Demo B）
5. **Merkle Root を計算する。** データを1つ変えたとき、順序を変えたときの Root を比べる。
6. **Merkle Proof の仕組みを理解する。**（6章。実装は Advanced A）
7. **データ件数 N とハッシュ計算回数の関係を分析する。**
8. **全件検証と Merkle Proof 検証の理論計算量を比較する。**（`complexity.py`）
9. **結果を表・グラフにまとめる。**（`benchmark.py` の TODO）
10. **理論計算量と実測結果を考察する。**

## 12. Advanced Research：発展課題

必須課題を終えたチームが挑戦する課題です。**Advanced A〜E のうち、チームの能力と時間に応じて1つ以上を選択**してください。すべてを実装する必要はありません。

### Advanced A：Merkle Proof の実装と計算量評価

**目的**：Merkle Proof による効率的なデータ検証を実装する。

1. Proof 生成関数を実装する（`merkle_tree.generate_proof`）。
2. Proof 検証関数を実装する（`merkle_tree.verify_proof`）。
3. 正しいデータの Proof を検証する。
4. 改ざんしたデータの Proof を拒否する。
5. Proof 中のハッシュを変更した場合を調べる（左右の情報を入れ替えた場合も）。
6. N を増やして Proof の長さを測定する。
7. 全件検証との計算量を比較する。

**特に、N が2倍になったときに Proof の長さがどう変わるか**を調べてください。

### Advanced B：データ変更と Merkle Tree の増分更新

**目的**：既存の Merkle Tree で1件のデータが変更されたときの更新コストを調べる。

1. 葉データを1件変更する。
2. 変更した葉から Root までのハッシュを再計算する（`merkle_tree.update_leaf` の TODO）。
3. 木全体を再構築する場合と比較する。
4. ハッシュ計算回数を比較する。
5. 実行時間を比較する。
6. N の増加による性能差を調べる。

既存の木の**全階層を保持している**場合、変更した葉から Root までの**経路だけ**（log₂N 個の親）を計算し直せば済みます。経路以外のノードの値は変わらないからです。

### Advanced C：改ざん位置とハッシュチェーンの検証コスト

**目的**：ブロックの改ざん位置が、検証・再計算のコストに与える影響を調べる。

1. B 個のブロックを生成する。
2. 先頭付近のブロックを変更する。
3. 中央付近のブロックを変更する。
4. 最終ブロックを変更する。
5. 改ざん検出結果を比較する。
6. 後続ハッシュの再計算回数を比較する（改ざんを隠すために必要な計算量）。
7. チェーン全体の検証時間を比較する。

**改ざんした位置**と、**先頭から検証したときに最初に問題が見つかる位置**を区別して分析してください（改ざんしたブロックの `hash` も計算し直すと、検出される位置がずれます）。

### Advanced D：Merkle Tree の一般化

**目的**：データ件数や木の構造が変わった場合の計算量を調べる。

1. N が 2 のべき乗でない場合を扱う。
2. 奇数個のノードの処理方法を設計する（例：最後のノードを複製する、そのまま上の階層に持ち上げる、RFC 6962 のように「N 未満の最大の 2 のべき乗」で左右に分ける）。
3. Proof の長さを比較する。
4. 二分木と多分木（例：4分木）を比較する。
5. 分岐数と Proof サイズの関係を調べる。
6. 分岐数とハッシュ計算回数の関係を調べる。

> 奇数個のノードの扱い方は**実装によって異なります**。採用した規則を明記してください。規則によっては、異なるデータ列が同じ Root になる問題が起こることがあります（例：最後のノードを複製する方式で、`[A, B, C]` と `[A, B, C, C]` の Root が一致する）。

### Advanced E：ハッシュチェーンと実用ブロックチェーンの違い

**目的**：教材用の簡易ブロックチェーンと、実用的な分散台帳の違いを理解する。

1. ハッシュチェーンの改ざん検出の限界を調べる。
2. 改ざん後にハッシュをすべて再計算した場合を検証する（`blockchain.py` の TODO）。
3. 信頼できる外部のハッシュ値による検証を考える。
4. 分散合意の役割を調査する。
5. 電子署名の役割を調査する。
6. Merkle Root がブロックに含まれる理由を説明する。
7. Proof of Work と Proof of Stake の基本的な違いを調べる。

> ⚠️ 実際の暗号資産ネットワークへの接続やマイニングは行わないでください。

## 13. 実験条件と評価指標

### 記録すべき実験条件

- PC 環境（CPU、メモリ）、OS、Python のバージョン
- データ件数 N、ブロック数 B、各データのバイト長
- 改ざんの位置と方法
- 測定回数と、平均値・中央値などの集計方法

### 評価指標

| 指標 | 内容 |
| --- | --- |
| ハッシュ計算回数 | 何を1回と数えたか（葉・内部ノード・ブロック）を明記する |
| 実行時間 | 測りたい処理だけを `time.perf_counter()` で挟む（データ生成・表示は含めない） |
| Proof のデータサイズ | 兄弟ハッシュ 32 バイト × 個数 ＋ 左右の情報 |
| メモリ使用量 | `tracemalloc` などで測定（木の全階層を保持するコスト） |
| 検出結果 | 改ざんを検出できたか、どの位置で検出されたか |

### 注意

- **構築（O(N)）と検証（O(log N)）を混同しない。**
- **全件検証と Merkle Proof 検証は、前提と検証対象が違う**ことを明記して比較する。
- 1回の処理が短すぎるときは、何回も繰り返して合計時間を測る。
- Big-O は漸近的な評価であり、実測時間そのものではありません。
